# API / 协议 / 微服务
输入：契约、调用方、身份、幂等、错误和异步完成语义。按协议处理，不给RPC/WebSocket强套HTTP。
- 字段、类型、必填、范围、精度、编码、额外字段和兼容。
- 认证、对象/角色/租户权限；拒绝后检查无副作用。
- 业务码、金额、状态、数据库约束和下游动作；HTTP200不等于成功。
- 幂等分开测顺序重复、并发重复、超时重试和重复回调。
- GraphQL错误和部分成功；RPC deadline；WebSocket握手、重连、顺序和背压约定。
- Mock声明范围，契约通过不证明真实集成。
- 跨服务部分成功、补偿和最终一致性，不默认全部原子完成。
证据：脱敏请求响应、关联ID和数据/消息。无DB访问时可用查询API补充，但不声称事务已直接验证。
正：响应成功但库存未扣则失败。负：接受200/400/500任意状态制造通过。

## 可执行案例：登录后更新订单
前置：两个测试用户A/B、各自订单、一个无效Token、可查询的业务键。用项目现有客户端，或标准库urllib/Postman验证；Java项目可沿用JUnit/REST Assured，Python沿用pytest。不要为工具更换产品栈。

| 场景 | 请求与断言 | 数据或外部检查 |
|---|---|---|
| 正常更新 | A的Token修改A订单，核对业务码/金额/状态 | 重新GET，核对版本及金额 |
| 水平越权 | A的Token修改B订单，断言约定拒绝码 | B重新GET，金额/状态未变 |
| 字段边界 | 数量0、负数、最大值及邻点 | 无部分库存扣减 |
| 批量赋值 | 加入owner_id、role等不可写字段 | 归属与角色未改变 |
| 超时重试 | 同一幂等键在结果未知时重发 | 只有一个业务结果/外发动作 |
| 契约变化 | 缺可选字段、旧调用方、未知字段 | 按兼容约定判断，而非全拒或全收 |

可信测试代码的最小响应断言：
~~~python
assert response.status_code == expected_http_status
body = response.json()
assert body['order_id'] == created_order_id
assert body['amount_cents'] == 10000  # 来自独立验收规则
assert query_order(created_order_id)['owner_id'] == user_a_id
~~~
金额使用产品约定精度；不要用浮点相等检验货币。接口返回订单ID后应保存作证据，不固定查询“最近一笔”，否则并行互相污染。

## 失败取证与无DB降级
保存脱敏请求、业务ID、返回、时间、trace ID和查询结果。没有DB权限时：先读业务状态→执行→通过用户视角及管理员测试查询交叉读取→在约定窗口轮询下游状态→检查重复业务键及审计接口。此证据支持可观察结果，不直接证明事务隔离或内部无瞬时写入；不可观测副作用标inconclusive。
如果系统只有200但业务失败，按业务码和内容判断；GraphQL部分成功逐字段判断。负向对照应隔离修改返回金额或去掉授权检查，原断言必须失败；不在真实系统上撤销权限以制造问题。
