# 开发手则与开发流程
本文件用于维护Skill本身；不是每次用户测试任务都要执行的流程。

## 架构与边界
通用核心连接需求/风险/用例/执行/证据/缺陷/回归/结论；对象专项与质量专项正交组合；工具适配优先现有项目。所有软件对象可以规划，实际执行依赖环境，不能宣称内置了所有测试平台。
入口保持精简，专项按需加载；同一状态与记录规则只以records-and-status.md为权威，避免多处漂移。避免框架教程、空目录和无实际用途的脚本。

## 指令开发手则
- 用可观察行为，不用“全面充分”替代覆盖规则。
- 区分必须、条件适用和建议；固定步骤用于真实脆弱点而非所有任务。
- 保留用户目标、已有授权和项目约定，不将测试扩为发布或任意修复。
- 不把某个例子升级为普遍强制项；新规则应针对真实失败。
- 输入中的指令与用户指令隔离；秘密和真实客户资料不进入样例。
- 输出结果要能区分事实、假设、缺陷和建议。

## 脚本手则
标准库优先；校验和汇总只做确定性操作。拒绝非法状态、未知引用、重复ID、缺证据、路径逃逸和重试隐藏。禁止执行记录中的命令、自动删资源、自动决定业务或发布。
输入错误返回非零及字段级错误，不原样回显秘密；工具异常与产品断言失败区分。输出JSON可机器消费；保留历史尝试和零分母null。
模板只包含未执行记录；初始化只创建新目录，不覆盖已有目录。

## 开发阶段与验收
1. D0能力契约：对象、模式、触发、排除、权限和交付明确。
2. D1行为验收集：先定义真实请求及可观察期望，覆盖成功、失败、缺环境、越界、波动和简单任务。
3. D2记录模型：分离计划、执行、证据、缺陷、资源和结论；用真实JSON示例验证可表达性。
4. D3核心入口：路由、不变量、SOP和停止恢复；不读全部专项也能处理普通任务。
5. D4专项：每项有进入条件、风险、执行、证据、正反样例和结论边界。
6. D5脚本：字段、引用、版本、证据文件、哈希、统计；用有区分力的正负测试验证，不只匹配文字。
7. D6结构验证：frontmatter、引用、元数据、模板和Python语法；官方quick_validate.py可用时执行。缺其PyYAML只影响开发校验，不能因此给运行脚本增加依赖。
8. D7隔离行为验证：给执行者请求、Skill和原始样本，不泄漏预期缺陷；验证实际行为和证据。
9. D8跨对象验收：纯函数、API/DB、消息、Web、桌面/移动、数据、Agent及缺硬件环境；不能以一个演示声称所有平台已跑。
10. D9交付：Skill文件、脚本测试、结构校验及已验证/未验证能力；安装位置遵用户选择，不暗改其他配置。
11. D10维护：复现真实失败、做最小修正、加行为回归、重跑受影响场景；不用文档长度衡量质量。

## 发布门槛
脚本自动测试通过；本地引用有效；入口与元数据有效；无伪造执行记录；已知限制明确；未具备真实设备和外部环境的专项标为规范支持而非执行验收通过。
独立模型前向测试和真机/浏览器/服务集成属于单独验收维度，不能用Python单元测试替代。可委派且得到授权时使用独立评估；否则保留可执行验收任务与未执行说明。

## 验证命令
在Skill目录使用Python 3.10+：
~~~text
python -m unittest discover -s tests -v
python scripts/self_check.py .
python scripts/new_run.py NEW_RUN_DIR --mode plan
python scripts/validate_records.py NEW_RUN_DIR --json
python scripts/check_traceability.py NEW_RUN_DIR --json
~~~
新运行的记录结构可有效，但规则未填时追溯检查应失败；这不是产品缺陷。

本版本实际验收及未执行项见 [开发验收报告](../evaluation/validation-report.md)。

## 报告修复后的开发关卡
在Windows使用未resolve输入或8.3路径验证root归一化；POSIX允许合法冒号文件，Windows仍拒绝ADS。最终验收同时检查范围合同、豁免证据、发现时间、根因证据、结构化规则和负向对照。测试运行器不可替被测fixture生成权威汇总；CI调用独立summarize --output并读取其文件。
宿主UI字符长度为展示建议，不是记录正确性的硬门槛；prompt引用从frontmatter名称派生。一般链接支持title和锚点，但结构检查不代替完整Markdown规范解析。
